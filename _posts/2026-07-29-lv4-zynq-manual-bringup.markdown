Lv4의 목표는 하나의 칩 안에서 서로 다른 두 세계를 만드는 것이다 — Zybo Z7-20(Zynq-7000,
듀얼 Cortex-A9)의 코어0에서는 리눅스가 돌고, 코어1에서는 OS 없는 베어메탈 프로그램이
독립적으로 돈다. 리눅스 커널엔 이걸 위한 `remoteproc`라는 표준 프레임워크가 있는데,
이번 시리즈는 그 프레임워크를 바로 쓰지 않고 **프레임워크가 내부적으로 하는 일을 먼저
손으로 재현**하는 것부터 시작했다 — 나중에 뭘 자동화하는 건지 모른 채로 자동화 도구를
쓰고 싶지 않아서였다.

## 코어1이 안 죽고 대기하는 방법 — 처음 가정이 틀렸다

Zynq-7000은 전원이 켜지면 `BootROM → FSBL → U-Boot → Linux` 순으로 부팅하는데, 코어1은
BootROM 단계부터 코어0과 동시에 실행을 시작한다. 문제는 우리가 코어1엔 별도로 다른
프로그램을 올릴 거라, 코어1이 그때까지 크래시 없이 얌전히 대기해야 한다는 것.

처음엔 ARMv8/PSCI 계열에서 흔한 "spin-table"(정해진 주소를 폴링하며 WFE로 저전력
대기하다 SEV로 깨어나는 방식)을 가정하고 넘어갈 뻔했다. 근데 이 프로젝트에서는 뭔가를
가정할 때마다 실제 커널 소스로 확인하는 버릇이 있어서(Lv2~3에서 여러 번 이 버릇 덕에
잘못된 가정을 미리 잡아냈다), 로컬에 있던 mainline 커널 소스
(`arch/arm/mach-zynq/{platsmp.c,slcr.c,headsmp.S}`)를 까봤다.

**틀렸다.** 실제로는 이랬다:

- 코어1은 폴링하며 대기하는 게 아니라, **SLCR**(System Level Control Registers, 시스템
  제어 레지스터 블록)의 `A9_CPU_RST_CTRL` 레지스터에 있는 RST·CLKSTOP 비트로 **하드웨어
  적으로 리셋 고정**돼 있다 — 명령어가 하나도 안 도는 진짜 정지 상태다.
- 깨우는 절차는 물리주소 `0x0`에 2개 명령어짜리 "트램폴린"을 심고(`ldr r0,[pc,#0]` →
  `bx r0`), 그 옆 워드에 진짜 목적지 주소를 써넣은 다음, SLCR 레지스터에서 리셋 비트를
  클리어하는 것.
- **SEV/WFE는 전혀 안 쓰인다.**

SGI(코어간 소프트웨어 인터럽트)나 spin-table 같은 ARM 표준 패턴에 익숙해질수록 "이 칩도
당연히 그렇겠지"라고 짐작하기 쉬운데, Zynq-7000은 ARMv8 이전 세대(Cortex-A9, ARMv7-A)라
그 표준이 아직 없던 시절 설계다. 짐작 대신 소스를 깐 덕에 이 차이를 착수 첫날에 잡았다.

## 트램폴린 — 실제로는 이렇게 생겼다

```asm
_start:
    ldr r0, [pc, #0]   ; pc는 이 명령어 주소+8, 즉 다음 워드를 가리킴
    bx  r0             ; r0에 든 주소로 점프
    .word 0            ; 점프주소 자리 — U-Boot에서 나중에 값 채워넣음
```

`ldr r0, [pc, #0]`이 성립하는 이유는 ARM이 실행 중 `pc`를 읽으면 "자기 주소+8"이 나오는
파이프라인 특성 때문이다. 이 코드가 주소 `0x0`에 있으면 `pc`는 `0x8`을 가리키고, 그 자리
(`.word 0`)에 진짜 목적지 주소를 나중에 써넣으면 된다.

U-Boot 콘솔에서 이 전체 절차는 이렇게 된다:

```
fatload mmc 0 0x0 trampoline.bin      # 트램폴린을 리셋벡터 자리에
fatload mmc 0 0x10000000 hello.bin    # 코어1이 실행할 진짜 프로그램
mw.l 0x8 0x10000000                   # 트램폴린 점프주소 patch
mw.l 0xf8000008 0xDF0D                # SLCR 언락(보호 레지스터라 매직값 필요)
mw.l 0xf8000244 0x22                  # 코어1 강제 리셋
dcache flush
mw.l 0xf8000244 0x00000000            # 리셋 해제 → 코어1 실행 시작
```

## Vivado 없이, mainline U-Boot 하나로

Zynq 개발이라고 하면 보통 Xilinx Vivado부터 떠올리는데, 이번엔 그게 전혀 필요 없었다.
mainline U-Boot을 뒤져보니 Zybo Z7 보드의 DDR/클럭 초기화 데이터
(`board/xilinx/zynq/zynq-zybo-z7/ps7_init_gpl.c`, 원래 Vivado가 생성해주는 그 데이터)가
이미 들어있었고, U-Boot의 SPL이 FSBL 역할을 그대로 대신했다. `mkimage -T zynqimage`가
Xilinx의 독점 `bootgen` 툴도 대신해줘서, 정말로 `make zynq_zybo_z7_defconfig && make`
만으로 부팅 이미지가 나왔다.

가는 길에 자잘한 함정도 있었다 — WSL2가 USB 대용량저장장치 드라이버 자체를 안 갖고 있어서
(`/lib/modules`가 아예 없는 구조) SD카드를 못 인식했고, Windows에서 직접(Rufus로 순수
FAT32 포맷) 구워서 우회했다. 그리고 부팅 모드 점퍼가 JTAG 위치에 꽂혀있어서 첫 시도는
완전 무음이었다 — 흔한 초심자 함정.

## 캐시가 두 번 발목을 잡다

트램폴린과 SLCR 절차 자체는 맞았는데, 첫 시도에서 코어1이 아무 반응이 없었다. 코어1
펌웨어(`0x10100000` 주소를 계속 증가시키는 단순 카운터)를 올렸는데, U-Boot에서
`md.l 0x10100000`으로 찍어봐도 값이 `0xffffffff`에서 안 움직였다.

**원인 1 — 코어0의 쓰기가 코어1한테 안 보임.** 트램폴린/펌웨어를 SD카드에서 읽어 메모리에
쓴 게 코어0(U-Boot) 자신의 캐시에만 반영되고, 실제 DRAM엔 아직 안 내려가 있었다. 코어1은
코어0 캐시와 무관하게 물리 DRAM만 보니, 옛날 쓰레기값을 읽고 있었던 것. `dcache flush`를
리셋 해제 직전에 추가해서 해결.

**원인 2 — 이번엔 반대로, 코어0 자신의 읽기가 캐시에 갇힘.** flush를 추가하고 나니 값이
한 번은 바뀌었는데, 그 뒤로 또 멈췄다. 이번엔 코어0이 `md.l`로 읽을 때 자기 캐시의 예전
스냅샷만 계속 보여주고 있었다 — 코어1은 실제로 계속 DRAM을 바꾸는데, 코어0 눈엔 고정된
것처럼 보인 것. **매 읽기 직전에도** `dcache flush`를 넣어야 했다.

한 번의 성공적인 캐시 처리로는 부족하고, "쓰기 쪽"과 "읽기 쪽" 양방향을 따로 챙겨야
한다는 게 이 두 버그의 교훈이었다.

## 최종 증명

```
dcache flush
md.l 0x10100000 1
10100000: 4cd4b699
dcache flush
md.l 0x10100000 1
10100000: 4d68054e
dcache flush
md.l 0x10100000 1
10100000: 4dfb1334
```

매번 flush 후 읽으니 값이 확실히, 계속 증가했다. **코어1이 remoteproc 없이, 순수
SLCR 리셋 제어+트램폴린만으로 독립 기동돼 계속 실행 중임을 최종 증명.**

다음 편은 이 위에 인터럽트를 얹는 이야기다 — 코어0과 코어1이 SGI(소프트웨어 생성
인터럽트)로 서로를 "kick"하게 만들고, 실제 리눅스 커널 모듈로도 검증하는 과정. 그리고
이번엔 L1 캐시만 flush해서는 안 풀리는, 한 겹 더 깊은 캐시 문제를 만난다.
