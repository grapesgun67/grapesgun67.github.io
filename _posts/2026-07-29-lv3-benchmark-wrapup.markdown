[1편]({% post_url 2026-07-29-lv3-v4l2-pipeline %})에서 캡처를, [2편]({% post_url
2026-07-29-lv3-dmabuf-runtime-pm %})에서 zero-copy 공유와 전원관리를 확인했다. Lv3의
마지막 목표는 "이해했다"를 넘어 **수치로 증명하는 것**이었다.

## 대조군이 없는 문제

zero-copy 전/후를 비교하고 싶은데, 우리 파이프라인(CFE→PiSP BE)은 처음부터
dma-buf zero-copy로 설계돼 있어서 "zero-copy 안 썼다면"의 대조군이 시스템에 아예
없다. 해법은 실제 memcpy 대역폭을 따로 실측하고, 우리가 이미 아는 프레임
크기·주기와 결합해 "복사했다면 얼마나 손해였을지" 계산하는 것이었다.

## `-O2`가 벤치마크를 통째로 지워버리다

`memcpy_bench.c`(실제 프레임 크기 23,887,872바이트로 200회 반복 측정)의 첫 결과는
**1,779,357GB/s** — 물리적으로 불가능한 숫자였다. 원인은 컴파일러였다. `dst`
버퍼를 아무도 읽지 않으니, `-O2`가 그 memcpy 루프 전체를 "죽은 저장(dead store)"으로
판단하고 통째로 최적화해서 지워버린 것이다. 코드는 있는데 실제로는 아무 일도 안
일어나고 있었다.

```c
asm volatile("" : : "r"(dst), "r"(src) : "memory");
```
컴파일러 배리어를 추가하고, 체크섬으로 실제 복사가 일어났는지 재확인한 뒤에야
정상적인 숫자가 나왔다: **3.85 GB/s**.

## Before/After

```
memcpy 1회당 시간: 6.21ms
30fps 프레임 예산(33.33ms) 대비 비중: 18.63%
```
zero-copy가 없었다면 아무 실질 처리도 안 하는 "그냥 옮기기"만으로 프레임 예산의
거의 1/5을 쓰고, CPU 코어 하나를 그만큼 지속 점유했을 것이다.

실제 스트리밍 중 `mpstat`으로 잰 CPU 점유율은 **전체 코어 평균 1% 미만**이었다.
처음엔 "특정 코어(CameraManager 스레드가 돌던 코어)에 몰릴 것"이라 예측했는데,
부분적으로만 맞았다 — 진짜 핵심은 코어 쏠림이 아니라 **압도적으로 낮은 절대치**였다.
파이프라인 전체가 DMA로 돌아가서, CPU는 인터럽트 처리와 가벼운 3A 계산 정도만 하기
때문이다.

## 지연 — 커널과 유저스페이스, 두 개의 시각을 동시에 잰다

`v4l2_latency.c`로 raw bypass 경로에서 60프레임을 받으며 매 프레임마다 ①커널이
`v4l2_buffer.timestamp`에 찍은 시각(하드웨어가 완성한 진짜 시각)과 ②`DQBUF`에서 우리
프로그램이 깨어난 시각을 동시에 기록했다. 왜 두 개를 따로 재느냐면, 이렇게 안 하면
"하드웨어가 원래 이런다"와 "전달 과정에서 지연이 추가됐다"를 구분할 방법이 없기
때문이다.

```
커널 타임스탬프 기준 프레임 간격: 평균 33.321ms (편차 0.002ms)
유저스페이스 체감 간격:          평균 33.321ms
전달 지터(유저 체감 - 커널 실제): 평균 ~0ms, 최대 5μs
```

수정발진기 기반 하드웨어 클럭이 만드는 프레임 타이밍은 편차 0.002ms로 사실상 완벽하게
일정했고, 커널→유저 전달 과정에서 추가되는 지연은 최대 5μs로 무시할 수준이었다.
`1000÷33.321 ≈ 30.01fps` — libcamera 자체 로그(`30.01 fps`)와도 정확히 일치했다.

## 종합

| 지표 | 결과 |
|---|---|
| 프레임레이트 | 30.01fps (2회 교차검증) |
| 지연 | 커널→유저 전달 지터 평균 ~0ms, 최대 5μs |
| CPU 점유율 | 전체 코어 평균 1% 미만 |
| zero-copy 비교 | 이론상 손해 6.21ms(예산의 18.63%) vs 실측 <1% |

## 챕터를 닫으며

Phase A~D를 진행하면서 실제 채용공고도 같이 조사했는데, 42dot·Samsung LSI·Qualcomm
모두 V4L2/MIPI-CSI 브링업을 명시하고 있었고, 여러 공고에서 공통으로 나타나는 실무
워크플로(`media-ctl`로 링크·포맷 설정 → `v4l2-ctl` raw 캡처로 최하위 검증 →
GStreamer/libcamera 등 상위 스택 통합)가 이 세 편에서 밟아온 순서와 그대로 일치했다.
Qualcomm의 실제 업스트림 드라이버([`qcom_camss`](https://docs.kernel.org/admin-guide/media/qcom_camss.html))
문서를 보면서, 우리가 만진 구조가 "이 정도만 알면 된다"가 아니라 실제 산업 표준
그 자체라는 확신이 들었다.

Lv3는 여기서 일단 마무리한다(하드 디버깅 케이스스터디 심화와 업스트림 기여는 보너스로
남겨두고). 다음 챕터([챕터4 — Zybo 이기종 AMP]({{ "/" | relative_url }}))는 완전히
다른 종류의 문제로 넘어간다 — 카메라처럼 "이미 있는 파이프라인을 이해"하는 게 아니라,
한 칩 안에서 리눅스와 베어메탈이 서로 다른 코어에서 동시에 돌게 만드는 이야기다.
